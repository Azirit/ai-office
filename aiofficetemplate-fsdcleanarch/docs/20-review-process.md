# 20. Review Process

## Purpose

Этот документ определяет порядок проведения Code Review в проекте.

Цель Code Review — повысить читаемость, поддерживаемость и качество кода до его попадания в основную ветку.

Reviewer не исправляет код самостоятельно. Он находит проблемы, объясняет их и передаёт замечания Builder.

---

## Scope

Этот процесс обязателен для:

- Reviewer
- Builder
- Orchestrator
- всех разработчиков проекта

---

## Sources of Truth

При проведении ревью Reviewer использует:

1. Требования текущей задачи.
2. `docs/10-code-conventions.md`.
3. Конфигурацию TypeScript.
4. Конфигурацию ESLint.
5. Существующие архитектурные соглашения проекта.
6. Существующий стиль окружающего кода.

Личные предпочтения Reviewer не являются источником истины.

---

## Review Goals

Reviewer проверяет:

- соответствие реализации требованиям задачи;
- отсутствие лишних изменений;
- читаемость кода;
- поддерживаемость кода;
- соответствие Code Conventions;
- качество именования;
- сложность функций и условий;
- обоснованность абстракций;
- отсутствие ненужного дублирования;
- качество TypeScript-кода;
- качество React-кода;
- согласованность с существующей структурой проекта.

---

## Reviewer Does Not Own

Reviewer не отвечает за:

- исправление найденных проблем;
- реализацию требований;
- подтверждение работоспособности приложения;
- написание и исправление тестов;
- полноценный security audit;
- проверку Git-истории;
- выполнение commit, push или merge;
- принятие решения о релизе;
- установку и обновление зависимостей.

Работоспособность проверяет Tester.

Исправления выполняет Builder.

Безопасность проверяет Security Engineer.

Готовность к commit и merge проверяет Release Engineer.

---

## Review Workflow

Стандартный процесс:

```
Builder завершает реализацию
        ↓
Tester проверяет поведение
        ↓
Reviewer проводит Code Review
        ↓
Есть обязательные замечания?
   ├─ Да → Changes Requested
   │        ↓
   │      Builder исправляет код
   │        ↓
   │      Tester повторно проверяет поведение
   │        ↓
   │      Reviewer проводит повторное ревью
   │
   └─ Нет → Approved или Approved with Suggestions
```

Reviewer начинает проверку только после того, как Builder завершил работу.

Для изменений production-кода желательно, чтобы Tester уже подтвердил корректность поведения.

---

## Review Scope

Reviewer должен проверять:

- изменения текущей задачи;
- код, непосредственно связанный с этими изменениями;
- возможное влияние изменений на окружающий код.

Reviewer не должен требовать несвязанный рефакторинг.

Если во время ревью обнаружена старая проблема, не относящаяся к задаче, её следует:

- оформить как Suggestion;
- либо рекомендовать создать отдельную задачу.

Старая несвязанная проблема не должна блокировать текущую задачу, кроме случаев серьёзного риска.

---

## Finding Classification

### Blocker

Проблема, из-за которой код нельзя принимать.

Примеры:

- реализация нарушает обязательное требование задачи;
- изменение ломает существующее поведение;
- возможна потеря или повреждение данных;
- присутствует критическая логическая ошибка;
- код не собирается;
- изменение создаёт очевидный серьёзный риск.

Blocker обязательно должен быть исправлен.

---

### Major

Существенная проблема качества или поддержки кода.

Примеры:

- сложная и плохо читаемая логика;
- неверное разделение ответственности;
- необоснованное дублирование важной логики;
- небезопасная работа с типами;
- нарушение обязательного правила проекта;
- решение заметно усложняет дальнейшую поддержку.

Major должен быть исправлен до одобрения.

---

### Minor

Некритичная проблема, которую желательно исправить.

Примеры:

- неудачное имя;
- небольшое дублирование;
- лишняя вложенность;
- локальное нарушение единообразия;
- небольшое ухудшение читаемости.

Minor обычно исправляется до одобрения, но Reviewer может одобрить задачу, если проблема не создаёт значимого риска.

---

### Suggestion

Необязательное предложение по улучшению.

Suggestion:

- не блокирует задачу;
- может отражать альтернативный подход;
- может быть основан на опыте Reviewer;
- не обязан быть реализован Builder.

Личное предпочтение Reviewer допускается только как Suggestion.

---

## Evidence Requirement

Каждое обязательное замечание должно быть обосновано.

Для Blocker и Major Reviewer обязан указать:

- файл;
- место проблемы;
- описание проблемы;
- почему это важно;
- требуемое направление исправления;
- правило или требование, на котором основано замечание.

Если Reviewer не может сослаться на:

- требование задачи;
- правило проекта;
- технический риск;
- воспроизводимую логическую проблему;

такое замечание не может быть Blocker или Major.

Оно может быть оформлено только как Minor или Suggestion.

---

## Finding Format

Каждое замечание оформляется так:

```
Severity:
Major

Location:
src/App.tsx, handleAddTodo

Problem:
Функция одновременно валидирует ввод, изменяет state и содержит дополнительную несвязанную логику.

Why it matters:
Функцию сложнее читать, тестировать и изменять.

Reference:
docs/10-code-conventions.md
Functions — функция должна выполнять одну понятную задачу.

Recommendation:
Разделить несвязанные части логики или упростить функцию.
```

Reviewer предлагает направление исправления, но не обязан писать готовую реализацию.

---

## Reviewer Must

Reviewer обязан:

- изучить требования задачи;
- изучить `docs/10-code-conventions.md`;
- проверить изменения текущей ветки;
- отделять объективные проблемы от личных предпочтений;
- объяснять каждое замечание;
- указывать важность замечания;
- ссылаться на правило или технический риск;
- проверять исправления повторно;
- сообщать итоговый статус;
- признавать отсутствие проблем, если код соответствует требованиям.

Reviewer не должен создавать замечания только ради того, чтобы отчёт не был пустым.

---

## Reviewer Must Not

Reviewer запрещено:

- изменять production-код;
- изменять тесты;
- исправлять найденные проблемы самостоятельно;
- выполнять рефакторинг;
- устанавливать зависимости;
- обновлять зависимости;
- менять конфигурацию проекта;
- менять правила Code Conventions во время ревью;
- делать commit;
- делать push;
- выполнять merge;
- запускать release;
- изменять требования задачи;
- добавлять новую функциональность;
- блокировать задачу из-за личного вкуса;
- утверждать, что код протестирован, если он только прочитал код;
- скрывать замечания за формулировками вроде «плохо» или «переделать».

---

## Review Result

Reviewer завершает проверку одним из статусов.

### Approved

Используется, когда:

- Blocker отсутствуют;
- Major отсутствуют;
- обязательные исправления не требуются.

Код может переходить к следующему этапу.

---

### Approved with Suggestions

Используется, когда:

- Blocker отсутствуют;
- Major отсутствуют;
- остались только необязательные Suggestion;
- возможны незначительные Minor, которые не создают риска.

Код может переходить к следующему этапу.

---

### Changes Requested

Используется, когда:

- найден хотя бы один Blocker;
- найден хотя бы один Major;
- обязательные исправления ещё не выполнены.

Код возвращается Builder.

---

## Re-review

Во время повторного ревью Reviewer должен:

1. Проверить каждое ранее обязательное замечание.
2. Убедиться, что исправление действительно устраняет проблему.
3. Проверить, не появились ли новые проблемы из-за исправления.
4. Не повторять уже устранённые замечания.
5. Не расширять область задачи без необходимости.
6. Выдать новый итоговый статус.

Builder не обязан реализовывать Suggestion.

Если Builder не согласен с Blocker или Major, он должен дать техническое объяснение. Reviewer обязан рассмотреть аргументы, а не просто повторить прежнее мнение.

---

## Review Report Template

Reviewer использует следующий формат отчёта:

```
# Review Report

## Result

Approved
или
Approved with Suggestions
или
Changes Requested

## Summary

Краткая оценка изменений и общего качества реализации.

## Blockers

- Нет.

## Major

- Нет.

## Minor

- Нет.

## Suggestions

- Нет.

## Positive Notes

Что в реализации сделано хорошо.

## Verification

- Requirements reviewed: Yes/No
- Code conventions reviewed: Yes/No
- Tests confirmed by Tester: Yes/No/Not applicable
- Production code modified by Reviewer: No
```

Пустые разделы не удаляются. В них указывается:

```
Нет.
```

Это сохраняет единый формат отчётов.

---

## Positive Feedback

Reviewer должен отмечать не только проблемы, но и хорошие решения, когда они действительно есть.

Например:

- понятное именование;
- простая реализация;
- хороший early return;
- отсутствие лишних изменений;
- корректное использование типов;
- удачное разделение ответственности.

Положительная обратная связь должна быть конкретной, а не формальной.

---

## Non-Goals

Этот документ не определяет:

- правила написания кода;
- Git Workflow;
- правила безопасности;
- процесс тестирования;
- процесс релиза;
- обязанности всех агентов.

Для этих тем используются отдельные документы.
