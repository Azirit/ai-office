# 10. Code Conventions

## Purpose

Этот документ определяет единые правила написания кода в проекте.

Главная цель — сделать код понятным, единообразным и удобным для поддержки.

Данный документ является основным источником истины по стилю и качеству кода.

---

## Scope

Правила обязательны для:

- Builder
- Reviewer
- Всех разработчиков проекта

---

## Authority

При возникновении конфликтов используется следующий порядок приоритетов:

1. Требования задачи.
2. Этот документ.
3. Конфигурация TypeScript.
4. Конфигурация ESLint.
5. Существующий стиль проекта.
6. Официальные рекомендации React.
7. Официальные рекомендации TypeScript.

Личные предпочтения разработчика не являются правилом проекта.

---

# General Principles

## Rule 1

Код должен быть понятен без объяснений автора.

---

## Rule 2

Простое решение предпочтительнее сложного.

---

## Rule 3

Не добавлять функциональность, отсутствующую в задаче.

---

## Rule 4

Не выполнять несвязанный рефакторинг.

---

## Rule 5

Не создавать абстракции без реальной необходимости.

---

## Rule 6

Если код становится сложным для чтения — его необходимо упростить.

---

# Naming

## Variables

Использовать camelCase.

---

## Components

Использовать PascalCase.

---

## Types

Использовать PascalCase.

---

## Boolean variables

Начинать с:

```
is
has
can
should
```

---

## Event handlers

Начинать с

```
handle
```

Например

```
handleSubmit
handleDelete
handleChange
```

---

# Functions

## Rule 1

Функция должна выполнять одну понятную задачу.

---

## Rule 2

Название функции должно описывать действие.

---

## Rule 3

Использовать ранний выход (Early Return), если он улучшает читаемость.

---

## Rule 4

Избегать глубокой вложенности.

---

## Rule 5

Избегать большого количества параметров.

---

# TypeScript

## Rule 1

Не использовать `any`, если существует безопасная альтернатива.

---

## Rule 2

Предпочитать вывод типов (Type Inference), когда он очевиден.

---

## Rule 3

Не использовать type assertion (`as`) без необходимости.

---

## Rule 4

Использовать `unknown`, если тип действительно неизвестен.

---

## Rule 5

Публичные API должны иметь явные типы.

---

# React

## Rule 1

Не изменять state напрямую.

---

## Rule 2

Не использовать useEffect без необходимости.

---

## Rule 3

Не создавать компонент только ради нескольких строк JSX.

---

## Rule 4

Не хранить производные данные в state.

---

## Rule 5

Соблюдать Rules of Hooks.

---

# Imports

## Rule 1

Удалять неиспользуемые импорты.

---

## Rule 2

Не создавать циклические зависимости.

---

## Rule 3

Группировать импорты логически.

---

# Comments

## Rule 1

Комментарий объясняет "почему", а не "что".

---

## Rule 2

Не комментировать очевидный код.

---

## Rule 3

Удалять закомментированный код.

---

## Rule 4

TODO должен содержать ссылку на задачу, если она существует.

---

# Formatting

Форматирование определяется:

- ESLint
- Prettier (если будет использоваться)

Reviewer не делает замечаний по форматированию, если его автоматически исправляет formatter.

---

# Exceptions

Допускается нарушение правил, если:

- это повышает читаемость;
- существует объективная техническая причина;
- правило конфликтует с требованиями задачи.

Нарушение должно быть обосновано.
