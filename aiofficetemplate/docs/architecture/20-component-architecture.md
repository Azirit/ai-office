# Архитектура компонентов

## Принципы

1. **Один компонент — одна ответственность.** Каждый компонент делает одну понятную вещь.
2. **Простое решение предпочтительнее сложного.** Не создаём абстракции без реальной необходимости.
3. **State поднимается вверх.** Данные хранятся как можно выше по дереву компонентов.
4. **Дочерние компоненты получают данные через props.** Не используем context без необходимости.

---

## Когда разбивать на компоненты

Разбиваем, когда:
- Компонент делает больше одной вещи (рендер + логика + состояние)
- JSX-дерево становится сложным для чтения
- Одна часть логики переиспользуется в разных местах
- Тестирование одной части требует мока другой

Не разбиваем, когда:
- Компонент < 50 строк и понятен
- Разбиение добавляет больше файлов, чем решает проблем
- Нет переиспользования

---

## Правила для компонентов

### Именование
- Компоненты — PascalCase
- Функции-обработчики — `handle*`
- Пропсы — объект с описательными именами

### Пропсы
- Пропсы — входные данные компонента
- Callback-пропсы начинаются с `on*` (onAdd, onDelete, onChange)
- Не передаём объекты глубже 2 уровней

### State
- Храним state как можно выше
- Локальный state — только то, что нужно компоненту
- Не храним производные данные в state

---

## Когда выносить логику в хук

Выносим, когда:
- Логика управления state повторяется в нескольких компонентах
- Компонент содержит > 30 строк логики (не считая JSX)
- Логика не зависит от DOM

Не выносим, когда:
- Логика специфична для одного компонента
- Хук будет содержать < 10 строк
- Нет переиспользования

---

## Потоки данных

```
Parent (state + логика)
    ├── Child A (props: данные + callbacks)
    └── Child B (props: данные + callbacks)
```

**Правило:** данные текут сверху вниз, события идут снизу вверх.

---

## Что НЕ делаем

1. **Не разбиваем на компоненты раньше времени.** Если компонент понятен — оставляем.
2. **Не создаём контекст без необходимости.** Props-дерево предпочтительнее.
3. **Не используем Redux/Zustand** без объективной причины.
4. **Не выносим стили в отдельные файлы** до объективной необходимости.
5. **Не создаём абстракции «на вырост».** Решаем текущую проблему.
